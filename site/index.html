A SMALL GATEWAY, A CLEAR BOUNDARY

Your comment is the starting point.

01 / CONNECT

Meet work where it lives

Receive signed webhooks from Forgejo, GitHub, or GitLab. A polling ingester is also available when you cannot create a webhook.

02 / ROUTE

A mention becomes a request

The gateway verifies the event, authorizes the user and repository, and passes the location URL and message to an agent.

03 / ACT

The agent owns the work

The agent reads the context, edits the checkout, validates its changes, and responds on the forge. The gateway does not build its context.

CHOOSE YOUR TOOLCHAIN

Different agents.
One entry point.

Use Codex, Pi, Claude Code, Antigravity CLI, Kimi, or a configured custom agent. Adapter defaults stay in charge of model selection unless you explicitly configure or request a model.

Explore the configuration ↗

Keep the conversation going

Per-thread sessions preserve context. Supported adapters accept follow-ups during a run; others queue the next turn.

See what is happening

Web status, run details, and live output make running and queued work visible. Human mentions can become browser notifications.

Control who can run what

User and repository policies gate requests. Configured agent users run as separate Linux accounts through the cgroup executor.

START WITH A CHECKOUT

Give your next issue
an agent.

Build the binary, configure your forge and agent users, then validate the setup. You will need Rust, a Linux host with cgroup v2, a forge token, and an authenticated agent CLI.

Deployment guide ↗
TERMINAL / QUICK START
git clone https://github.com/AgentaaU/forge-bot.git
cd forge-bot
cargo build --release

cp config.example.toml forge-bot.toml
$EDITOR forge-bot.toml

# Verify configuration before serving
cargo run -- check
cargo run -- serve

Configure at least one agent user and exactly one default user. Follow the deployment guide for service installation, credentials, and webhook setup.
